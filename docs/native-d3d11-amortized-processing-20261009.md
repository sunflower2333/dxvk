# DDI11 immediate submission amortized processing

Microsoft's local `windows-driver-docs/windows-driver-docs-pr/display/changes-from-direct3d-10.md` requires DDI11 drivers to call `pfnPerformAmortizedProcessingCb` on the thread that entered the DDI after immediate-context submission, or a comparable natural frequency. DDI11 no longer gets this work automatically through `pfnRenderCb`. The callback trims runtime high-watermarks and deferred destruction. Microsoft also requires explicit Flush to offer deferred-destruction cleanup even with an empty command buffer. Both Vista and Windows 7 DDI11 revisions share this contract.

The native RuntimeGpu bridge now requests an opportunity only after a successful, validated RenderCb submission. RuntimeService services it after backend jobs return and retired backend references drain; RuntimeGpu submission/allocation guards and the service queue mutex are gone. The recursive entry mutex remains held to serialize the immediate context while allowing same-thread nested DDIs. No callback runs on a DXVK/Mesa worker, or on a timer. An explicit DDI11 Flush also requests an opportunity, including an empty Flush.

The oldest matching caller Scope grants at most one invocation for that original DDI. This includes nested Flush and repeated Flush retirement passes. The opportunity is consumed before the callback executes, so nested submission or Flush cannot recursively invoke it; newly requested work remains pending for the next permitted DDI. Backend construction buffers are internal initialization, before the DDI table exists: the handler is installed after successful backend construction and before callable entries are published.

The closure retains a weak independent Device owner and reads the current runtime-owned callback slot for every opportunity. DestroyDevice marks the owner retired and closes runtime service; the suspended outer operation pins the independent owner without accessing reclaimed runtime private bytes. A callback may destroy children, replace its slot, or destroy the device. The typed device wrapper does not issue a late SetError callback if the owner was retired before an exception propagated. D3D9/10 install no amortized handler and preserve their previous behavior. Existing controlled test-device tables with a NULL amortized slot retain their mock behavior; real DDI11 runtime tables supply the callback. No adapter masks, standard factory, version negotiation, registry policy or default Mesa selection changes are included.

The source-linked runtime GPU fixture adds actual production RuntimeGpu and typed DDI11 controls for failed submission, two successful submissions coalescing once, original caller/thread checks, an empty Flush, replacement of the runtime callback slot, nested Flush with query destruction and PAGE_NOACCESS, successful release of the submitted allocation from the callback, and destruction/reclamation of the device with both its private storage and real callback-table page made PAGE_NOACCESS during the callback. The final case raises a C++ exception after retirement to check the late-error guard. Existing D3D10 runtime teardown and nested resource/view retirement controls remain intact.

Validation before a VM run is limited to actual SDK strict x86/x64 COFF compilation of `umd_ddi.cpp`, `umd_runtime_gpu.cpp` and `tests/umd-runtime-gpu.cpp`. The new controls must execute on Windows before their runtime behavior is claimed as proven. Their marker is `D3D11 amortized processing PASS:`; the overall runtime-GPU CHECK count remains dynamic and is read from the actual successful run.

A controlled native build uses the existing runtime-GPU Meson source/link recipe in `src/umd/meson.build`: fixture `tests/umd-runtime-gpu.cpp`, production `umd_runtime_gpu.cpp`, `umd_runtime_query.cpp`, `umd_ddi.cpp`, `umd_allocation.cpp`, `umd_shader.cpp`, `umd_shader11.cpp`, and the pinned DXBC dependency implementation. Retain the actual selected EWDK compiler/reference/import libraries and existing raw-output/retained-process discipline. The fixture substitutes WARP for the embedded device factory, so it proves callback and lifetime contracts rather than ordinary hardware rendering, Present, DWM or default replacement.
