# Reversible D10-only SYSTEM runtime binding experiment

The later same-owner DX9/9Ex extension is described in
[system-runtime-dx9-binding-extension-20261009.md](system-runtime-dx9-binding-extension-20261009.md).
This document records the original D10 profile and frozen648f boundaries.

This packet supplies a concrete controller for the immutable unregistered
frontend/probe source `8eeb20cfa91f01ec15712c6964af4c3ba676d8e6`. It does not
activate a workflow, register a candidate here, clear production requirements,
change a signed KMD/image or perform a target operation. ROOT owns all future
Windows commands and original collection. The frozen97bb version has a known
snapshot-before-lease race and must not execute Apply. This follow-up acquires
the lease before its authoritative backup and restores only intent-backed work.

The controller's default is a readonly exact tuple and genuine KMT-name
snapshot. `-ApplyReviewedTuple` explicitly enables one temporary adapter-wide
experiment. It replaces only the second native `UserModeDriverName` string.
The first DX9 string, third DX11 string, every original terminator/padding byte,
`UserModeDriverNameWoW` and `InstalledDisplayDrivers` remain unchanged during
binding. The backup retains native and WoW views, value existence, numerical
registry kind and raw bytes. Restore replays and independently reads all six
values, including absent values. HKLM\SYSTEM views can alias; the source does
not invent an independent x64 registration name.

This is adapter-wide, not process-local. Existing Mesa modules are left loaded,
but another process creating a new D10 device during the window could observe
the temporary entry. The routine measures original DWM/Explorer owners and
installed KMD service/image/hash/signature/INF/provider/version before/after;
it cannot guarantee isolation merely because old modules remain loaded.
Ordinary acceptance and default replacement remain false in every output.

## Concrete lifetime and restoration sequence

1. Resolve the caller's exact present `PCI\VEN_1AF4&DEV_1050` display instance
   to its actual class key. For Apply, acquire the global adapter validation
   lease and refuse an outstanding rescue task before the authoritative backup.
   Hold that lease through preparation and cleanup. Snapshot six raw values and all three original KMT
   names for the supplied nonzero LUID. No hardcoded target LUID, PIDs or key
   number is used.
2. Require exact frontend/core/probe, installed SYS, separately pinned progress
   runner and token-helper hashes. Require a complete separately reviewed
   native matched Vulkan payload: a pinned ICD JSON, its actual library, and
   the core's exact sibling `winevulkan.dll`. Candidate frontend and native
   core share a protected reviewed directory. No binary is installed/copied
   by this controller.
3. Protect configuration/backup/release files with administrator/SYSTEM write
   permission and desktop USER read permission. Give USER Modify only on the
   separate output directory. Copy/pin controller support scripts into the
   protected directory before any service task loads them.
4. Launch a separate SYSTEM Task Scheduler restoration task, including an
   at-startup recovery trigger. It obtains and retains the original controller
   process handle/start time, writes its armed checkpoint, and restores on
   owner exit, source error or a 120-second absolute deadline. It does not
   inherit the SSH controller's job. A startup recovery can restore bytes
   after a surprise reboot; it cannot guarantee no earlier boot component
   observed the temporary entry. This routine never initiates a reboot.
5. Launch the existing desktop account with Interactive/Limited task semantics
   from the proven D3D9 lifetime helpers. The worker checks native ARM64, SID,
   desktop session, non-elevation and medium integrity. Before any child, it
   assigns itself an unnamed kill-on-close job. Its inherited probe children
   cannot survive worker/task/session loss. Failure to establish this job
   stops before tuple mutation.
6. The worker runs the immutable probe's five typed `--entry-negative` controls
   through the `7def540f...` progress runner before declaring
   readiness. The core remains unloaded in these controls. Genuine KMT queries
   must match all three original tuple strings and the supplied LUID.
7. Only after both watchdog and worker readiness does the controller take the
   restore mutex, recheck the raw original tuple, publish/flush a protected
   mutation-intent record, then write/read the single
   candidate D10 string. It checks the untouched WoW/installed values. A
   restoration/deadline checkpoint prevents later mutation or factory start.
8. The worker re-queries actual KMT names and launches mode10 of the immutable
   probe. Only the worker/child receives the reviewed Vulkan ICD/logging
   environment. It uses genuine SYSTEM factory/DXGI modules, actual adapter
   LUID/private identity, exact frontend/core modules, draw/readback and Present.
   The progress runner retains the actual OS process handle and raw streams.
9. The actual probe's `HELD` output triggers restoration. The controller
   writes a protected proof only after all raw original values read back;
   only then does it publish release permission. The worker queries KMT again
   while the actual probe is held, records all three names, and releases the
   probe's fresh session-local event. The event is not a restoration proof.
10. The worker reaps the actual child and stores the progress runner's actual
    exit/status/pipe fields. Controller and watchdog remove only their owned
    tasks. Failed cleanup, stale KMT names, input changes or desktop/KMD changes
   fail the controller; partial original files remain available. If intent is
   absent, cleanup cancels without writing the unused backup and labels fresh
   raw readback equality separately from actual restoration. A failed
    rescue task is retained for independent recovery review.

The bounded worker job protects child lifetime; the independent SYSTEM task
protects registry lifetime. The script does not claim that these Windows
mechanisms have been executed in this packet. Actual owner-loss/timeout/task
and registry controls remain necessary before accepting a target experiment.

## Cache diagnosis and bounded refresh path

The local Microsoft registration docs place D10 in the second tuple slot and
D11 in the third, and describe runtime loading of the registered UMD. They
do not define a live cache-refresh or process-local registry ABI. Project
findings at `.planning/dxvk-umd/findings.md`2235+ retain the actual earlier
DX9 attempt: the temporary first-slot change read back, KMT still returned
Mesa, the runtime made no frontend call, and the exact tuple was restored.
That is evidence that registry-only selection previously failed on this
target, not proof that a device restart or reboot is required or sufficient.

On a cached-name result, the new probe deliberately fails before factory
creation at `effective-kmt-frontend-selection-required`, then holds for restore.
This diagnoses the selection boundary without blaming missing shader/caps
semantics or declaring WARP success to be hardware acceptance.

An explicit `-WaitForReviewedRefresh` variant makes a concrete next experiment
possible without adding a reset to the controller. After writing the candidate
slot it publishes `controller\candidate-tuple-written.json` with the watchdog
armed, and waits up to30seconds for an administrator-protected
`controller\refresh-complete.json`. ROOT can independently execute/record a
reviewed exact-devnode operation during this window. Local Microsoft
`windows-driver-docs/windows-driver-docs-pr/devtest/pnputil-command-syntax.md`
139+ documents `pnputil /restart-device <instance ID>`; no `/reboot`, wildcard,
second VM or package install belongs in this bounded operation.

The checkpoint must have schema1, exact instance/LUID, `reboot_requested=false`,
actual exit0 and at least two `actual_originals` path/SHA entries for ROOT's
genuine owned process/raw operation. It grants no success by itself: the worker
still opens the original exact LUID and requires the genuine candidate KMT
name before the ordinary factory. If LUID changed, the original probe stops;
ROOT restores/re-queries and prepares a fresh run with that actual LUID. If
desktop owners changed, the strict continuity result fails and must be treated
as a separate refresh/recovery experiment rather than uninterrupted Mesa DWM.

A refresh that leaves a candidate KMT name cached after raw tuple restoration
also fails. ROOT must independently reestablish the original effective name
and desktop state before any default-driver claim. If a clean VM reboot is
actually required, first restore/verify the tuple, then use the registered VM's
daemon path and clean guest shutdown, retaining one VM and8192MiB. This packet
contains no VM/image command and never moves `/back` backups.

## D10 and D11 remain distinct

The controller always invokes mode10 and changes only D10's tuple string.
Actual successful telemetry must show the private typed legacy D10.0 entry.
The frontend does not export `OpenAdapter10_2`. Current modern core pipeline
caps remain zero under missing production requirements. Probe mode11 remains
a separate selection/caps diagnostic; no old-entry fallback or D11 hardware
support is inferred from D10 success. Default Mesa remains until separately
verified admission/replacement work is complete.
