# DXGI residency and priority, and the normal runtime entry

This slice is based on `90fb093ce2a85af12de9028076517f1045c36e61`. It adds typed DXGI1.0 and DXGI1.1 residency/priority entries; it leaves the immutable native feature-level admission predicates unchanged. Private development adapters still select exact 10.0, 10.1 and 11.0 device tables. They are separate from Microsoft's normal runtime entry points.

## Implemented behavior

`QueryResourceResidencyDXGI` validates every driver resource handle against the live resource registry, captures its owned runtime allocation and reservation, and queries the exact KMT handles through the original `pfnQueryResidencyCb`. The callback receives owned arrays and `hResource == NULL`, so no runtime resource cookie is passed as a KMT handle. Only allocations attached to present, created-shared and opened-shared resources are currently tracked by this layer. Backend-only resources return `DXGI_DDI_ERR_UNSUPPORTED`; no residency is inferred from backend existence or a CPU mapping. Duplicate resource handles retain one output per requested resource.

The callback's three official residency values are mapped field by field to DXGI's separate enum. An evicted result returns `S_NOT_RESIDENT`, otherwise any shared-memory result returns `S_RESIDENT_IN_SHARED_MEMORY`, and an all-GPU result returns `S_OK`. No output is published until all callback statuses and resource identities pass validation. Invalid/unwritten raw enum words, callback HRESULT failure, non-`S_OK` kernel success, reset/generation change, or resource/device retirement preserve the entire output array. The bounded implementation accepts at most 4,096 resources, checking the actual `SIZE_T` field before narrowing or reading arrays.

`SetResourcePriorityDXGI` resolves and pins the same allocation ownership, then forwards the original 32-bit priority through `pfnSetPriorityCb`. Zero and `0xffffffff` are legitimate priorities. The kernel callback's HRESULT is preserved on failure; unexpected positive kernel status is rejected. Retirement during a callback returns device removal. An active policy callback cannot recursively invoke another policy callback. Neither entry creates a device/context/allocation, submits GPU work, maps data, or changes capability advertisement.

The two kernel callback addresses are copied from slots2/3 of the original Vista `D3DDDI_DEVICECALLBACKS` prefix. The adapter and `RuntimeMemory` never reread that borrowed table after device creation. D3D10/D3D11 core and DXGI callback tables retain their existing live runtime ownership.

## Normal Microsoft runtime blockers that remain

1. `OpenAdapter10` rejects a non-admitted requested 10.0/10.1 interface before hardware identity querying. `OpenAdapter10_2` performs normal identity/open but returns zero supported versions, zero 3D pipeline support, zero private-device size and `DXGI_ERROR_UNSUPPORTED` for device creation. The reason is the immutable contract policy, not a missing named export or a driver registration switch. The private named adapter entries set development admission only; they cannot be used as proof of an ordinary runtime replacement.
2. Complete rendering-allocation residency remains unfinished. Shared/present resources pair a CPU-visible KMD backing with a separately allocated embedded rendering cache. This slice forwards the backing's actual residency; it cannot yet describe every allocation the embedded renderer uses for rendering. The official DXGI contract requires selecting the rendering allocations, including an appropriate set for resources with multiple allocations. Before public admission, the bridge needs a resource-to-renderer/KMT allocation ownership API and aggregate queries/priority forwarding over that complete set, with reset and alias lifetime coverage. The existing immutable `CompleteResources`/`PrimaryAndDxgi` gates continue to prohibit claiming that this backing-only path establishes complete resource residency.
3. The DXGI table still lacks `pfnBlt`, `pfnSetDisplayMode`, `pfnGetGammaCaps`, and, for a 1.1 table, `pfnResolveSharedResource`. Existing `Present` supports a windowed blit with implicit destination, source subresource0, and a one-mip/slice/sample RGBA8 or BGRA8 resource. Primary descriptors are rejected; combined present+shared ownership is rejected. Ordinary display replacement requires the requested DXGI presentation paths, ownership and synchronization to be implemented. In particular, `BltDXGI` is responsible for resolve/conversion/stretch/rotation combinations, while shared-resource resolution must flush partial commands before handing off ownership. Full-screen SetDisplayMode additionally needs a genuinely primary-marked allocation. These display operations are distinct from a headless ordinary D3D device-creation gate.
4. Opened resources remain limited to one allocation with the bridge's exact 80-byte metadata, plain RGBA8/BGRA8/BGRX8 Texture2D cache, one mip/slice/sample and no CPU mapping. Other shared/opened formats, multi-allocation ownership and relevant synchronization are still missing. A successful typed fixture cannot remove the broad opened-resource or complete-resource contract bits.
5. Full required shader, resource/format, MRT, predicate/query and stream-output semantics need a closed coverage matrix plus ordinary-runtime/Turnip acceptance. Texture1D/3D, typed10.1 cube arrays, null-GS output and bounded SM4.1/SM5 features have concrete implementations and controlled tests on this source; old broad contract comments are not evidence that those individual pieces remain absent. Conversely, those individual successes do not establish the complete profiles. D3D11 has additional compute/UAV, tessellation and shader-interface admission requirements. Command lists and free-threaded capability remain unadvertised.

The unchanged masks are 10.0 `0x17f`, 10.1 `0x37f`, 11.0 at FL10.0 `0x57f`, at FL10.1 `0x77f`, and at FL11.0 `0x3f7f`. This slice clears none of them. The next smallest ownership change is to expose the embedded resource's relevant allocations, rather than report an unqueried rendering image fully resident. Presentation then needs its own concrete DDI work; changing only registration or zeroing the contract mask is insufficient.

## Verification and native fixture inputs

`tests/umd-residency-transaction.cpp` exercises the production staging component with GCC and Clang ASan+UBSan: owned handles, all-or-nothing output, every later unwritten status, failed and unexpected-success HRESULTs, input/output aliasing, callback-side input mutation, late retirement, zero handles and the 4,096 bound. It prints `DXGI residency transaction PASS checks=102085`.

`tests/umd-dxgi-residency.cpp` links actual adapter/device/resource/retirement implementations and a fixture-only Microsoft WARP renderer. Six combinations cover exact 10.0/10.1/11.0 device tables and SDK-selected DXGI1.0/1.1 tables. It checks all three aggregate statuses and both ordering precedences; owned/present/shared/opened resources; unchanged failed outputs; raw invalid enum words; missing callbacks; foreign/no-access handles; reentrant callbacks; mutation then protection of the original kernel table; callback-side resource/device destruction and reset. Core/DXGI callback members remain alive through DestroyDevice. Its native execution remains pending an explicitly owned CPU slot. It does not prove hardware residency or ordinary-runtime admission.

Native link sources are that fixture plus `umd_adapter.cpp`, `umd_contract.cpp`, `umd_ddi.cpp`, `umd_shader.cpp`, `umd_shader11.cpp`, `umd_allocation.cpp`, `umd_runtime_query.cpp`, `umd_runtime_gpu.cpp`, and the repository's pinned DXBC dependency. The normal Meson target is `dxvk-umd-dxgi-residency-test`, with `d3d11` and existing DXBC dependencies; the portable target is `dxvk-umd-residency-transaction-test`. Use the established native first-party `/W4 /WX /MT /Zc:preprocessor` policy and unchanged dependency `/W3` policy. The additional SDK `d3d9.h` include supplies the official positive residency HRESULT constants; it does not route rendering through D3D9.

## Primary sources inspected locally

The exact WDK26100 `d3dumddi.h` declares both original-prefix callbacks and the resource-or-allocation-list structures; `dxgiddi.h` declares `Resources` as `SIZE_T` and the two distinct residency enums/tables. The local Microsoft DDI documentation contains the same rules:

- [DXGI base functions](https://learn.microsoft.com/windows-hardware/drivers/ddi/dxgiddi/ns-dxgiddi-dxgi_ddi_base_functions): required query callback, aggregate HRESULT precedence, rendering-allocation selection and Blt semantics.
- [DXGI1.1 base functions](https://learn.microsoft.com/windows-hardware/drivers/ddi/dxgiddi/ns-dxgiddi-dxgi1_1_ddi_base_functions): exact SDK table revision, primary display allocation and shared-resource flush.
- [QueryResidency callback](https://learn.microsoft.com/windows-hardware/drivers/ddi/d3dumddi/nc-d3dumddi-pfnd3dddi_queryresidencycb), [query structure](https://learn.microsoft.com/windows-hardware/drivers/ddi/d3dumddi/ns-d3dumddi-_d3dddicb_queryresidency): actual allocation handles and returned statuses.
- [SetPriority callback](https://learn.microsoft.com/windows-hardware/drivers/ddi/d3dumddi/nc-d3dumddi-pfnd3dddi_setprioritycb), [DXGI priority argument](https://learn.microsoft.com/windows-hardware/drivers/ddi/dxgiddi/ns-dxgiddi-dxgi_ddi_arg_setresourcepriority): arbitrary priority values and true runtime forwarding.
