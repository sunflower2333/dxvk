# Optional exact-instance lifecycle experiment in the existing binding owner

A real ordinary D11 attempt correctly changed native REG_MULTI_SZ slot2, but
fresh SYSTEM KMT queries still returned Mesa. The probe failed before factory,
loaded no candidate modules and rendered no pixels. Raw six-value and effective
Mesa restoration passed. Source audit found OS-managed UMD selection, not a
KMD filename cache. Cache timing remains an inference from that discrepancy.

The existing owner now has one explicit optional switch,
`-RootAuthorizeLifecycleRestart`, requiring `-ApplyReviewedTuple` and a reviewed
API/phase. The original D11 restriction remains D11Phase offscreen; the legacy
extension admits D9/9Ex offscreen or present and the existing D10 route, as
described in `native-system-legacy-lifecycle-20261009.md`. It excludes
`-WaitForReviewedRefresh`. Default behavior and production UMD/caps remain
unchanged. There is no second registry
owner, KMD install, disable/remove, reboot, image operation or VM operation.

The ordinary rendering attempt is bounded and adapter-wide. It uses the same
exclusive lease, raw six-value backup, prewrite recheck/durable mutation intent,
independent SYSTEM watchdog and startup rescue. The forward operation is genuine
System32 pnputil `/restart-device "<exact present instance>"` only, in a retained
20sec child and a controller kill-on-close job. Command exit0 is insufficient:
readiness requires the same healthy present devnode/class and KMD file/package,
exactly one paired160 private KMT identity, all returned enumeration handles
closed, and the expected three effective names. No guessed LUID or generation
increment is used. KMD StopDevice clears its LUID before drain; StartDevice
publishes the OS LUID only after successful initialization. Generation2 may
repeat after reconstruction.

The immutable recovery config keeps original_backup_luid. A protected forward
checkpoint carries the fresh paired160, forward_probe_luid and actual restart
receipt. The limited USER worker rechecks that entire current identity and same
instance/KMD, then gives forward_probe_luid to the unchanged ordinary SYSTEM D11
probe. Its strict nonsoftware vendor/device/LUID, typed11 FL10_0 factory, actual
module census, 512 literal pixels and complete adapter-retirement requirements
remain. Unused capability masks stay closed.

Normal settlement is ordered: durable raw6 replay/readback and release permission;
release/reap the original held device/context; prove worker and published probe
are gone; then reverse lifecycle recovery if effective names are still candidate.
No live GPU oracle spans reverse Stop/Start. A failed forward operation with no
current paired identity can still recover through the same exact installed
instance/class/KMD; full fresh readiness and Mesa names are required after
reverse. An absent or changed installed device/package denies that restart. Only an actual later boot permits an absent original job to represent completed
old-boot teardown; same-boot job absence denies recovery. The same cleanup/reverse hook runs
from normal failure, independent watchdog/owner loss and startup rescue. A
missing or blocked producer is stopped through its exact scheduled worker and
original job; Controller and the independent watchdog retain this protected-name
job before any candidate write. Recovery explicitly terminates it if needed and
waits for actual job accounting ActiveProcesses==0, including an unpublished
probe blocked before its hold checkpoint. Duplicate job handles never substitute
worker exit for completed teardown. A published original probe can only be killed after PID/start,
module path/hash and retained-handle validation. PID reuse establishes absence
of the old process and never authorizes killing the new one. Failed/unknown
producer closure denies the reverse restart and acceptance.

Reverse recovery records fresh restored_luid, paired160, all original effective
Mesa names, unchanged raw6/KMD and a healthy original desktop SID/session.
DWM/Explorer PIDs may change in this explicit lifecycle mode; default mode still
requires their original PIDs. A removed/hung device, failed/reboot-required
pnputil, missing current identity, foreign intent, incomplete cleanup, ineffective
Mesa selection or unhealthy desktop is a failed original. Raw restoration is
recorded even when subsequent recovery fails; the rescue task remains armed
when recovery is unproved. Hardware acceptance additionally requires the actual
positive worker/ordinary-probe evidence before reverse Stop/Start. Diagnostic
cleanup or successful recovery alone never counts as rendering success.

must retain the controller with a660sec outer deadline so recovery can finish.
